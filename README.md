# Unstuck

---

## 1. サービス概要

**このアプリの目的は、「報連相」を「勇気のいらないルーティン」へ変えることです。**

Unstuckは、若手エンジニアが抱える「報告の心理的ハードル」を解消するための進捗報告・詰まり管理ツールです。

**個人利用から始められるため、チームや上司への相談・承認なしに、今すぐ使い始められます。**

既存の管理ツールが「プロジェクトの進捗」にフォーカスする一方、本アプリは**「報告者の心理的安全性」**に特化します。
「今日のタスク」に対して進捗状況を選ぶだけの超軽量な報告スタイルを提供し、エンジニアが一人で抱え込みがちな「詰まり（Stuck）」から早期脱出します。



---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

SESエンジニアとして初めて既存システムの改修を担当したとき、インプットしなければならない資料の多さに一人でパニックになりました。
また、現場によってファイルのまとめ方・情報量・粒度がバラバラで、入場直後は「どの資料に何が書いてあるか」自体がはっきりわからないことも多々ありました。
他にも、現場ごとに新しい記述ルールや命名規則を覚えなくてはならなかったり、PMやリーダーとの距離感が違ったり、、

「何がわからないかがわからない」「誰に聞けばよいかわからない」状態で業務を進めた結果、以下のような負のスパイラルに陥りました。

```
何を/誰に質問すればいいかわからない（思考がまとまらずもがく）
↓
時間だけが過ぎていく
↓
どんどん深みにはまる（自分の中での情報の整理が長引く）
↓
スパイラルから抜け出せない
```
これは、ある程度経験を積んだ人にとっては「なんだ、そんなことか」と思う、取るに足らないことかもしれません。
人によって根性があったりや要領がよければ何とかなるのかもしれません。

でも、業界未経験だったあの頃の自分は毎日不安の中で仕事をしていました。
この経験から、「開発経験が浅いエンジニアのための、詰まっていることを気軽に伝えられる仕組みがあれば、もっと気楽に働けるのではないか」と感じました。

---

### 2-2. なぜそれが「気になった」のか

個人的に仕事する上での「不安の種」がとにかく多かったためです。
- 情報の整理が苦手で、「点の知識を線にする」のに人より時間がかかるため、様々なことを先輩や上司に確認しないと不安になるタイプだった。
　しかし現場に入って少しすると、「質問しすぎかな」「こんな簡単なこと聞いてもいいのかな」と声をかけることをためらう機会が増えていった。
- プロジェクト全体の中での自分の立ち位置を把握できていない（他の人より進捗が早いのか遅いのか、今はバッファを使っている状態なのか？など）と感じると心細かった。
- 人によって報連相の質が左右されることがあると感じた。人によって報告の量/粒度の違いがあることはもちろん、人間関係によっても言いやすい人とそうでない人がいた。
→　報連相を関係性や気合ではなく、「仕組み」で解決したいと思いました。

## 3. 課題の整理

### 3-1. 「詰まる」の定義

本アプリにおける「詰まる」とは、エラーが出ているかどうかに関わらず、**「前に進めない、でも何をすべきかわからない状態」**全般を指します。
具体的には、以下のような時間をすべて含みます。

**情報収集系**
- 資料の場所がわからない時間
- ネット検索してもヒットしない時間
- 複数の資料を読んだのに、どれが正しいかわからない時間

**思考整理系**
- 上司への質問をまとめる時間（粒度・参考情報の選定に悩む時間）
- エラーの原因が特定できず、何を調べればいいかわからない時間
- タスクの全体像が見えず、どこから手をつければいいかわからない時間

**対人コミュニケーション系**
- 質問するタイミングを見計らっている時間
- 「こんなこと聞いていいのか」と躊躇している時間
- 報告すべきか・まだ自分で解決すべきか判断できない時間

本アプリでは、進捗ステータスを以下の2択で報告します。

| ステータス | 意味 | 具体的な状態 |
|---|---|---|
| **進行中** | タスクが滞りなく進んでいる状態 | 手が動いている・解決の見通しがある |
| **奮闘中** | タスクに取り組んでいるが、一人では前に進みにくい状態 | 資料を探している・原因が特定できない・質問をまとめている・タイミングを見計らっている |

「奮闘中」はネガティブな報告ではなく、**「今ここに時間を使っている」という状態の記録**です。助けを求めているわけでも、できていないわけでもありません。

---

### 3-2. 表に見えている困りごと

- 報連相が遅れる・できない
- チームメンバーが「詰まっている」かどうかリーダーに伝わらない
- 経験が浅いメンバーほど「何を報告すればいいか」がわからない

---

### 3-3. 本当に解決したい課題は何か

**なぜ報連相が遅れるのか？**
→ 何を・どう報告すればいいかわからないから

**なぜわからないのか？**
→ 自分の状況を言語化できていないから。「進行中」なのか「奮闘中」なのかさえ整理できていない

**なぜ整理できないのか？**
→ 報告のフォーマットが存在しない。自分の現在地が把握できていない

→ **本当に解決したい課題：「詰まっていること」を、気軽に・仕組みとして伝えられる環境がない**

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

- **年齢：** 20〜30代前半
- **理由：** SESや受託開発に入りたての、実務経験1〜3年程度のエンジニア。ナレッジ蓄積文化が根付いていない現場に常駐している人が多い年代。
<br>　

- **生活・状況：** 複数のタスクを抱えながら、慣れないシステムの改修に日々取り組んでいる。詰まったときに「誰に・何を・どう聞けばいいか」迷うことが多い。
- **理由：** 上記の状況でこそ「詰まり報告を気軽にできる場所」が必要になる。
<br>　
　
- **環境：** リモートワーク、またはSES常駐。チャットでの報告が主な手段で、上司・リーダーと対面する機会が少ない
- **理由：** 対面ならではの「空気を読んで報告する」ができない環境で、報告のハードルはより高くなる。そして文章作成に苦手意識がある。

---

### 4-2. 自分とユーザーの距離

**対象ユーザー = 過去の自分**

SESエンジニアとして改修担当になりたての頃の自分が、このアプリのメインユーザーです。

最近は少しずつ、SESとして現場を転々とすることにも慣れてきました。
しかし、今でも時々
「あの時、もっと早くヘルプを呼べればよかったかな」
「もっと早く情報を整理できていたら、あの問題はもっと早く解決したかも」
と新人の頃に詰まった経験が頭をよぎるときがあります。

「詰まっていることをうまく伝えられず、スパイラルに陥った経験」が開発動機の核にあります。
あの時のくよくよしていた自分や、同じように悩んでいる駆け出しエンジニアを助けたい、という思いがあります。

**検証方針**
現在SESで働いている同僚や、RUNTEQの皆さんなど、想定ユーザーに近い人たちに実際に使ってもらい、「報告のハードルが下がったか」「継続して使えるか」をヒアリングしていく予定です。MVPリリース後、実際に1〜2週間使ってもらった上でフィードバックをもらう予定です。

---

### 4-3. 実際に使われる可能性について

- **最初に使ってくれそうな人：** RUNTEQの皆さん、SESで働きながら学習しているエンジニア
- **使う場面：** タスクが思うように進まないとき、今日の進捗を誰かに共有したいとき
- **今の代替手段：** Slack・Teams・Notion・口頭報告
- **置き換える理由：** 報告フォーマットが決まっていて、「進行中/奮闘中」の選択だけで気軽に報告できるから

---

### 4-4. 導入・継続の流れ

**本アプリは、個人利用から始めてチーム利用へと段階的に広げられる設計です。**
リーダーへの相談や承認なしに、自分一人でも使い始められます。

**① 個人利用フェーズ（MVPの想定）**
- **きっかけ：** 「報連相が怖い」「何を報告すればいいかわからない」と感じたとき
- **最初の一歩：** アカウント登録→を自分で報告タイミング、詰まり状況等を登録
- **使い続ける理由：** 毎回の報告が蓄積されることで、「自分がどこで詰まりやすいか」というパターンが見えてくる。自己理解が深まり、次回同じ場面での対処が早くなる

**② チーム利用フェーズへの自然な移行**
- 個人で使い続けるうちに、蓄積された詰まりパターンの記録がリーダーへの相談材料になる
- 「このツールで整理していたんですが、チームでも使ってみませんか？」と、データを見せながら自然な文脈で導入を提案できる
- 「新しいツールを入れてほしい」ではなく「自分の課題を解決したい」という文脈で話せるため、相談のハードルが下がる

**報告タイミングについて**

報告は1日1回固定ではなく、**ユーザー/チーム内で決定した任意のタイミングで設定できる。** リマインド通知もその設定時間に合わせて届く。人に管理されるのではなく、自発的に報告を促す設計とする。
（例：お昼前・15時・終業時の3回など、自分のリズムに合わせて設定）

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

| サービス名 | 競合の主なターゲットと特徴 | 本アプリが突く隙間 |
|---|---|---|
| **Jira / Backlog** | プロジェクト完遂が目的。チケット管理が主で、エンジニア個人の「迷い」や「詰まり」を拾う設計ではない | チケット化する前の「何がわからないかわからない」段階の感情を救い上げる |
| **Asana / Notion** | 情報の整理・可視化が目的。自由度が高い反面、報告の「型」を自分で作る必要があり、未経験者には負担 | 入力項目を極限まで絞り、書く内容に迷うコストをゼロにする |
| **gamba!** | 組織のエンゲージメントが目的。日報特化だが、エンジニア特有の技術的な詰まりやWBSとの連動が薄い | WBS（進捗）と詰まり（感情）を一体化し、エンジニアの業務文脈に特化 |
| **Slack / Teams** | リアルタイムの会話が目的。情報が流れてしまい、蓄積された「詰まりのパターン」を分析できない | 記録を「資産」として蓄積し、後からAI分析（将来機能）に活用できる構造を持つ |

---

### 5-2. それでも自分が作りたい理由

既存ツールは「管理する側（リーダー・PM）」のために設計されている印象が強いです。
管理者からタスクの進捗は見えますが、「今このメンバーが詰まっているかどうか」はわからず、個別に聞く必要があります。

また、報告するためのフォーマットが存在しないため、「何を・どう書くか」を毎回考えなければならなりません。
それ自体が、経験の浅いメンバーにとっての一つの心理的ハードルになっていると考えました。

競合サービスと本アプリの違いを一文で表すと、
「初心者エンジニアが、知識/経験量の違いによって業務の中で立ち止まってしまう瞬間を、効率面ではなく感情面でサポートできるサービス」

**→ つまり、「何をどう報告すれば良いかわからず、時間だけが過ぎていく若手エンジニアを、『奮闘中』のボタン一つで感情的な負担なく率直に報告できるよう助けるアプリ」**

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- **行動の変化：** 詰まったことをその日のうちに記録・報告できるようになる
- **気持ちの変化：** 「報告しなきゃ」という不安が「とりあえず入力した」という安心に変わる
- **考え方の変化：** 報連相は「周りとの関係性」や「気合」ではなく「仕組み」で解決できると思えるようになる

### 6-2. 価値を一文で表す

「報連相に苦手意識があるエンジニアが、心理的要因に左右されず、今日の詰まりを気軽に伝えられるようになるサービス」

## 7. このアプリで実現すること

### 設計思想

**【とにかく、悩む時間・ためらう時間を1秒でも減らす】**

- 余計な脳のリソースを使わないために、文字情報より視覚情報を重視する設計にします。
→文字を頭の中でかみ砕いてイメージするより、図として最初から目の前に提示する方が、瞬時に現在地を把握できる
→**WBS**と**カレンダー**の2視点を自由に切り替えて、「今自分がどこにいるか」を一目でわかる形で提供します。

- 「進行中/奮闘中」はリアルタイムのアラームではなく、**任意のタイミングで設定した定期報告の中の項目の一つ**とします。
→上司への即時通知ではなく、あくまで定時報告とすることで送信タイミングに迷う時間をなくします。

**効率的なタスク管理ツールやコミュニケーションツールはすでにいくらでも存在しますが、このアプリは「不安な感情」と「心理的負担」を解決することを目的とします。**

---

### このアプリが解決しないこと

設計の意図を明確にするために、あえて「やらないこと」は以下のとおりです。

- **リアルタイムのアラーム通知はしない：** 「詰まった瞬間に強制報告」ではなく、事前にタイミングを決めて定期報告できる設計を優先する
- **上司へのAI文章自動送信はしない：** 報告内容はあくまで本人が確認・判断する。AIが自動で上司に送信する仕組みは、報告者の自律性を損なうため採用しない
- **監視・評価ツールにはしない：** 詰まり状況の可視化は「助け舟を出すタイミングを知るため」であり、メンバーを管理・監視するためのものではない

---

### 画面設計の思想

**「画面を開いた瞬間に状況がわかる」をUI設計の基準とします**

- 入力項目は必須のみ。30秒以内に報告完了できる画面設計
- タスクの状態を色で直感的に判断できる（着手中：黄、終盤：青、奮闘中：赤）
- 文字を読まなくても、色と配置だけで全体像が把握できることを目指す
- スマートフォンからでも報告しやすいレスポンシブ対応

---

### 使い方

**① 個人で使う場合（MVP段階から対応）**
チームや上司への共有は不要。自分の詰まり状況を記録・蓄積することで、「自分がどこで詰まりやすいか」を可視化する。自己理解を深め、報告の精度を上げるための自己分析ツールとして活用できる。

**② チーム内で使う場合（本リリース以降で対応）**
メンバー全員が進捗と詰まり状況を入力することで、チーム全体の状況をリアルタイムで把握できる。リーダーは個別に進捗確認をする手間が減り、「助け舟を出すタイミング」を可視化できる。結果として、メンバーが心理的に頼りやすい環境が生まれる。

→ **MVPは個人利用を中心とした機能に絞り、本リリースで個人利用をさらに強化しつつ、チーム利用にも対応していく。**

---

### MVPで作る機能
**この時点で実装したい機能**
→個人で利用できる機能中心

**検証内容**
→個人での作業ログとして、継続して使うことができること。ストレスなく自分の状況を把握できること。

**① コンパクトな報告フォーム**
- 今日のタスク名
- 進捗ステータス（進行中 / 奮闘中 の二択、その他必要情報）
- 締め切り日
- 一言メモ（任意）
- 入力項目は最小限。深く考えずに30秒以内に入力完了できる設計を目指す

**② シンプルな進捗一覧表示**
- 報告を登録すると一覧に自動反映
- タスクの状態を色で直感的に把握できる
- 「タスク」軸で全体像を一目で把握できる

**③ 報告タイミングの任意設定＋リマインド通知（Web Push）**
- ユーザーが自分のペースで報告タイミングを設定できる
- 設定時間に未報告の場合、ブラウザのプッシュ通知が届く（Web Push使用）
- タスクで手一杯な状態でも見落としにくいようにアプリを開いていない状態でも通知を受け取れるようにする

---

### 本リリースで作る機能
**この時点で実装したい機能**
→個人利用機能の強化＋チーム利用機能への対応

**検証内容**
→個人としてもチームとしても、心理的負荷を抑えながら活用することができること。

**① WBSの視覚化**
- 進捗状況を帯グラフ・色分けで表示
- 「タスク」軸で全体像を視覚的に把握

**② カレンダー表示**
- WBSと同じデータを「期間」軸で表示
- WBSが「タスク」軸、カレンダーが「期間」軸の2つの視点を提供

**③ 管理者アカウント**
- リーダー・PM向けにチーム全体の詰まり状況を一覧表示
- 詰まりを見つけて叱責するためではなく、**「助け舟を出すタイミングを可視化する」**ためのツール
- 管理者の負担が減ることで余裕が生まれ、結果として経験の浅いメンバーが質問しやすい環境につながる
- MTG用の報告原稿をAIが自動生成・編集可能

**④ AIアシスト機能**
- 蓄積された詰まりデータから、自分の「詰まりやすい傾向」をAIが分析
- 次回のタスク見積もり精度の向上に活用

## 8. このアプリの懸念点とその対策

### 懸念点①：監視ツールになってしまう恐れ

- **何が問題になりそうか：** 進捗をわかりやすく「見える化」することで、管理者がメンバーを監視する目的で使い始める可能性がある
- **なぜそう思うか：** 「人を縛りすぎない」「監視ではなくコミュニケーションの補助」というコンセプトと矛盾する使われ方をされる恐れがある
- **対策：** 「このアプリは助け舟を出すタイミングを可視化するためのツールであり、監視ツールではない」というコンセプトをREADMEおよびUI上に明示する。詰まり報告はあくまで自己申告・定期報告の一項目であり、強制しない設計にする

---

### 懸念点②：チーム利用への移行ハードルが高い

- **何が問題になりそうか：** 個人利用で価値を実感した後、チームへの展開を提案する際に「新しいツールを導入したい」という相談自体がしにくい可能性がある
- **なぜそう思うか：** 報連相に苦手意識があるユーザーが対象のため、リーダーへの提案もためらいやすい。また既存のSlack・Teamsがすでに根付いている現場では「新しいツールを覚えるコスト」が障壁になりやすい
- **対策：** 「新しいツールを入れてほしい」という直接的な依頼ではなく、「個人で使って蓄積した詰まりパターンのデータをリーダーに見せる」という自然な文脈での提案を促す設計にする。データが会話のきっかけになることで、相談のハードルを下げる

---

### 懸念点③：記録が続かない

- **何が問題になりそうか：** 「記録するのが面倒」「忙しいと後回しになる」という理由で、そもそも使われなくなる
- **なぜそう思うか：** 記録ツールは継続が最大の課題。ツールがあっても習慣化しなければ意味がない
- **対策：** 入力項目を最小限にし（タスク名＋進行中/奮闘中の二択のみ）、ユーザーが任意設定したタイミングでリマインド通知を送る。「30秒で入力完了できる」をUI設計の基準にする

## 9. 今後の展開・発展の方向性

### 今考えている発展案

- **機能追加：** カレンダー機能、管理者向けダッシュボード、AI原稿生成、AIによる詰まり傾向分析
                →「管理者に余裕が出ると結果としてユーザーも仕事がしやすくなる」という考えから、双方にとって利用しやすい機能を目指す
- **データ活用：** 蓄積された詰まり記録から個人の詰まりパターンを可視化し、タスク見積もり精度の向上に活用
                　→自分自身を俯瞰的に見られることで、より状況を言語化でき、上司への報告ハードルが下がることを目指す
- **体験改善：** 報告入力を30秒以内で完了できるUIを目指す
                →ユーザーのフィードバックをもとにUIを継続改善し、最終的に報告することを意識しなくても自然に習慣化できる状態を目指す

## 10. 技術スタック

### 10-1. 使用予定の技術

- **フレームワーク：** Ruby on Rails
- **フロントエンド：** Hotwire（Turbo / Stimulus）
- **DB：** PostgreSQL
- **デプロイ先：** Render または Fly.io
- **通知：** Web Push（ブラウザプッシュ通知）

### 10-2. 技術選定の比較検討

| 候補 | 採用/不採用 | 理由 |
|---|---|---|
| Ruby on Rails | 採用 | Webアプリ開発に必要な機能が揃っており、日本語情報も豊富なため |
| Hotwire（Turbo/Stimulus） | 採用 | SPAを作ることが目的化するのを避け、スピード感をもって制作するため。React/Next.jsはMVP後に検討 |
| PostgreSQL | 採用 | Renderとの相性が良いため。将来的に蓄積された詰まりデータを全文検索したり、タグ付けによる傾向分析を行う予定のため、JSON型や全文検索に強いことがポイント |
| Web Push | 採用 | アプリを開いていない状態でもリマインド通知を受け取れるため採用。メール通知では習慣化を促す即時性が担保できないと判断した |
| ActionMailer | 不採用 | メール通知はユーザーが気づきにくく、報告の習慣化を妨げる可能性があるため |
| Slack Webhook | 不採用 | Slackを使用していない環境では利用できず、ユーザーの環境に依存するため。また、通知を受け取るためにユーザー自身が設定を行う必要があるため、導入ハードルが低くない。|

### 10-3. 今回チャレンジしたい点

- 報告フォームの入力UXを極限まで削ぎ落とす設計
- 色と配置だけで状態が伝わるUI実装

### 10-4. 不安な点

- 視覚的なUI実装（色分け・レスポンシブ対応）の難易度が現時点で未知数
- Web Pushの実装（Service Workerの登録・ブラウザ通知許可の取得・HTTPS環境の整備が必要）
